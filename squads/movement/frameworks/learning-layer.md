# Learning Layer — Insight, Playbook e Evolução

## Overview

O Learning Layer é o **sistema nervoso** do MMOS. Transforma dados, experiências e observações em conhecimento codificado — playbooks, checklists, frameworks atualizados e decisões melhores. Sem Learning, o movimento repete erros; com ele, cada ciclo é mais inteligente.

O ciclo de aprendizado:
1. **Insight**: observação ou dado que revela algo novo sobre o movimento, o público ou a cultura.
2. **Playbook**: processo documentado que codifica o que funciona (e o que não funciona).
3. **Checklist**: versão operacional do playbook — lista de ações para execução consistente.
4. **Framework Update**: quando insights acumulados justificam atualizar um framework existente do MMOS.

O Learning Layer opera em dois modos:
- **Contínuo**: coleta de insights semanais, atualizações incrementais.
- **Cíclico**: retrospectivas formais a cada trimestre com revisão de playbooks e frameworks.

## Princípios Aplicáveis ao MMOS

1. **Todo experimento gera aprendizado, não só resultado**. Falha documentada é mais valiosa que sucesso não analisado.
2. **Codifique antes de escalar**. Se algo funcionou, documente o processo ANTES de replicar.
3. **Playbooks são vivos**. Versionar e atualizar, nunca tratar como definitivo.
4. **Todos os agentes alimentam o Learning Layer**. Não é responsabilidade de um agente, é cultura do time.
5. **Aprender = mudar comportamento**. Se o insight não muda uma decisão ou processo, não foi aprendido de verdade.

## Protocolo de Aplicação

### Passo 1 — Captura de Insights
Formato padronizado para documentar insights:

```
INSIGHT #[número]
Data: [data]
Fonte: [dado, observação, feedback, experimento]
Descrição: [o que descobrimos]
Implicação: [o que isso muda no que fazemos]
Ação sugerida: [próximo passo concreto]
Confiança: [alta/média/baixa — quão certo estamos]
Responsável: [agente que vai atuar]
```

Insights devem ser registrados no mesmo dia em que são observados. Canal dedicado (Slack/Notion) para registro rápido.

### Passo 2 — Construção de Playbooks
Quando um processo se prova eficaz em 3+ repetições, codifique:

Estrutura de Playbook:
1. **Objetivo**: o que esse playbook resolve.
2. **Contexto**: quando usar (e quando NÃO usar).
3. **Pré-requisitos**: o que precisa estar pronto antes.
4. **Passos**: sequência de ações numeradas, com responsável e prazo estimado.
5. **Variações**: adaptações para contextos diferentes.
6. **Métricas de sucesso**: como saber se funcionou.
7. **Erros comuns**: o que evitar (aprendido na prática).
8. **Histórico de versões**: log de mudanças.

### Passo 3 — Derivar Checklists Operacionais
De cada playbook, extraia checklists para execução rápida:

Exemplo de checklist de "Lançamento de Ritual Semanal":
- [ ] Ritual tem nome e formato definidos.
- [ ] Data/horário fixos comunicados à comunidade.
- [ ] Template/prompt de participação criado.
- [ ] Primeiro ritual executado pelo líder como exemplo.
- [ ] 3 membros convidados como co-líderes da primeira edição.
- [ ] Métrica de sucesso definida (participantes, posts, sentimento).
- [ ] Review após 4 semanas agendada.

### Passo 4 — Retrospectiva Trimestral
A cada 3 meses, reunião formal:

**Agenda**:
1. Review do Health Score — tendência trimestral (15 min).
2. Top 10 insights do trimestre — o que aprendemos (20 min).
3. Playbooks criados ou atualizados (10 min).
4. O que funcionou e devemos ampliar (15 min).
5. O que não funcionou e devemos parar (15 min).
6. Frameworks do MMOS que precisam de update (10 min).
7. Prioridades de aprendizado para o próximo trimestre (15 min).

**Output**: documento de retrospectiva + lista de updates para playbooks/frameworks.

### Passo 5 — Atualização de Frameworks
Quando insights acumulados justificam mudança em um framework do MMOS:
- Documente a evidência que justifica a mudança.
- Proponha a alteração específica (o que era vs. o que será).
- Revise com pelo menos 2 agentes.
- Versione o framework (1.0 → 1.1) com changelog.
- Comunique a mudança ao time.

## Quando Usar / Não Usar

### Usar quando:
- Sempre. Learning é contínuo e não tem "fase de desligamento".
- Após cada experimento (documentar aprendizado).
- Quando algo inesperado aconteceu (positivo ou negativo).
- A cada trimestre (retrospectiva formal).

### Não usar quando:
- Nunca pule o Learning. É tentador ir direto para a próxima ação, mas o custo de não aprender é repetir erros.

## Agentes Responsáveis

| Agente        | Papel no Learning Layer                                     |
|---------------|-------------------------------------------------------------|
| Todos         | Registram insights no canal compartilhado.                  |
| Chief         | Facilita retrospectivas trimestrais. Prioriza o que aprender.|
| Impacto       | Cruza insights com dados de Measurement.                    |
| Architect     | Propõe updates em frameworks com base em insights.          |
| Ciclo         | Documenta playbooks e checklists operacionais.              |

## Inputs e Outputs

**Inputs**:
- Dados do Measurement Layer (Health Score, cohorts, experimentos).
- Observações qualitativas de todos os agentes.
- Feedback direto de membros da comunidade.
- Resultados de ativações (Activation Layer).
- Mudanças no ambiente cultural (Radar Layer).

**Outputs**:
- Banco de insights atualizado semanalmente.
- Playbooks documentados e versionados.
- Checklists operacionais para execução.
- Documento de retrospectiva trimestral.
- Updates em frameworks do MMOS (quando justificado).

## Exemplo Aplicado

### Caso: Aprendizados do primeiro trimestre de movimento de educação financeira

**Insight #47**: "Posts com cálculos concretos ('invista R$100/mês e tenha R$X em 5 anos') geram 4x mais saves que posts conceituais ('invista no seu futuro'). Implicação: público quer ferramenta prática, não inspiração genérica."

**Insight #52**: "O ritual de terça ('Terça da Grana') funciona melhor às 20h que às 12h. Membros participam mais à noite (contexto: trabalham durante o dia, pensam em finanças à noite)."

**Playbook derivado**: "Como criar post de educação financeira de alto save-rate" — inclui template de cálculo, estrutura de copy, horário de publicação, hashtags.

**Checklist derivado**:
- [ ] Post inclui número concreto (R$ ou %).
- [ ] Cálculo é verificável e honesto.
- [ ] CTA convida a salvar/compartilhar.
- [ ] Publicar entre 19h-21h.
- [ ] Usar template visual padrão.

**Framework update**: Berger STEPPS — adicionada nota interna: "Para este público, Practical Value (valor prático) é o princípio STEPPS mais forte. Priorizar sobre Social Currency em conteúdo recorrente."
